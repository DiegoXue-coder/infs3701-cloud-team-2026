# Objective, design synthesis and limitations — working draft

Prepared by DiegoXue-coder with Codex while Tenzin is unavailable. Adapted from the actual project and Alex's existing application/data explanation, whose authorship is retained. This is draft material for technical review, not a final approved report.

Reading Tracker is a lightweight shared reading library for a small study group. Members record a book title, reading status, pages completed, rating and optional note, then revisit the library to see current progress and summary statistics. The coursework deployment uses fictional records in one shared library. It does not implement private user accounts. Its practical problem is keeping the same reading information available when requests reach different servers, a process restarts, or one application instance is temporarily unavailable.

The group selected Option A, upgrading Diego's individual Reading Tracker rather than changing the business idea during infrastructure development. The upgrade separates the interface and application execution from authoritative reading data. A common public entry routes requests to two private application instances in different Availability Zones. Both use the same pinned Flask/Gunicorn release and the same DynamoDB table. Consequently, a user should not lose a saved reading record simply because the next request reaches the other host. A cloud deployment is useful here because a local process or single server would combine the interface and its availability into one failure point; the shared library needs a consistent reachable entry and independently retained data.

The intended workload is modest, intermittent browser activity with small independent records. Users add and inspect books rather than perform relational joins or complex transactions. DynamoDB fits that document structure and avoids operating a separate database server. The implemented strong-consistency reads simplify verification that a successful write can be read through either application instance. The trade-off is that the current homepage scans the table and derives statistics on each request. This is acceptable for a small course dataset but becomes increasingly expensive and slow as the library grows. A larger product would need bounded query access and a separate aggregation design, rather than assume that adding EC2 instances solves every bottleneck.

Two EC2/Gunicorn hosts preserve the existing application and provide an explicit, inspectable runtime and deployment version. This makes the infrastructure upgrade and request routing straightforward to demonstrate. It also creates operational work: maintaining the image and dependencies, rolling out a verified archive, monitoring process health, and recovering failed installations. The choice is justified by retaining the actual application and demonstrating those controls, not by claiming that serverless or another database is inherently too costly. A serverless redesign would change packaging and invocation behaviour and still require a durable shared data tier.

The evidence distinguishes intended resilience from observed results. A verified a fictional database write, readback from both labels, service from the surviving host while the writer was stopped, and retention of the same record after restarting that writer. Marina independently created and read a different record on both hosts, then observed thirty successful homepage requests, fifteen per label. These tests support the implemented shared-data and routing behaviour in those windows. They do not demonstrate an entire Availability Zone outage, unlimited capacity or uninterrupted service between samples. B's later HTTP503 preflight remains a dated failure observation; the service was separately verified again after starting the Lab on 10 November.

The implementation also has explicit security and scalability gaps. The public interface currently uses HTTP and has no login or CSRF protection, so only fictional data is permitted. AWS service access uses an instance role and restricted endpoint paths, while the supplied LabRole remains broader than an ideal application-specific role. No automatic capacity-scaling group was present in the current audit. These facts must remain visible in the final design and evidence checklist until resolved; fixed dual-instance load balancing cannot be relabelled as a completed demand-driven scaling test.
