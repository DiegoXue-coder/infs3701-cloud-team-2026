# 三个人同时开工：先独立做，再小步接起来

2026-10-31 修订。原任务把“可以开始准备”和“能够最终验收”都锁在上游整张卡之后，现已拆开。任务编号 T01–T24 保持不变，过去记录不删除、不冒充已完成。

## 三条主线从第一天同时开始

| 时间 | A：网络与部署 | B：应用与数据（暂定你） | C：测试与交付 |
| --- | --- | --- | --- |
| 今晚短会后 | 检查 Lab、画网络图、准备实例/入口配置 | 本地运行旧应用、确定字段、抽出数据读写接口 | 写测试清单、请求日志脚本、报告骨架和成本草稿 |
| 第 1–2 次独立工作 | 用简单健康检查假服务验证部署路径，继续网络/安全配置 | 本地替代数据层先验证逻辑；有本人权限时独立验证托管数据库 | 用同样的假服务验证测试脚本；准备监控指标与告警模板 |
| 第一次联合检查 | 提供部署环境参数和入口，接上 B 的可运行版本 | 交可启动代码和真实数据库读写步骤，替换假服务 | 用配置好的 BASE_URL 运行功能检查，记录实际问题 |
| 后续并行 | 双实例、负载均衡、TLS/安全修正，滚动更新图 | 共享数据验证、应用修复、可复现说明、报告章节 | 监控/告警实测、成本精化、录屏准备、证据核对 |
| 最后联合验收 | 展示最终资源与架构，配合受控故障操作 | 展示功能与数据保留，核对程序版本 | 记录分流/故障结果，核对五项交付和提交材料 |

不是每天每人都必须投入整天。今晚按各人课表约第一次短集成；各自独立工作按任务卡推进。

## 今晚只先约定五件小事

用约 20–30 分钟确认 [interfaces.md](interfaces.md) 中的草稿：启动方式、应用端口、健康地址、字段/数据访问约定、怎样识别响应实例。每项可以先标“暂定”，但三个人要用同一个版本。

这份小约定不是要求 B 先做完整应用。A 可以先接假服务；C 可以先对假服务写脚本；B 可以在本地验证数据读写。配置用变量，不把临时地址和资源 ID 写死。

## 每个人什么时候交什么

- A 尽早交“区域、子网/安全组方案、端口、访问方式、实际权限限制”；不必等整个 VPC 和 HTTPS 都做完才告诉 B/C 能用什么。
- B 尽早交“字段、启动命令、依赖、健康检查和示例请求”；不必等全部页面和数据库完成。
- C 尽早交“每个要求怎么测、请求结果如何记录、要保存哪些证据”；不必等 AWS 上线。

交接是提供一个可用的小版本或清楚的参数，不是把整张任务卡标完成。假服务、本地替代数据库和草稿必须标明，不能当真实 AWS 核心要求的证据。

## 系统怎样支持并行

- `start_after`：开始准备前的条件。除正式上传 T24 外，所有任务都是空列表，所以不需要等待其他整张卡复核完才能认领准备。
- `early_steps`：现在不等别人就可以做的具体动作，已经写入每张 Issue。
- `depends_on`：提交完整成果/复核完成前的条件。它不能被拿来阻止提前写代码、配置或测试。
- 已去掉无关条件：数据库改造不再等待邀请全员或完整 TLS 检查；成本估算不等安全验收；视频准备与录制不等完整报告；架构图滚动维护，不等故障测试整张卡完成。

AI 每次应优先续做本人当前任务，或选一项独立准备，不要一次认领八项。需要上游参数时先做可替换的草稿或假服务，明确还缺什么，并向对接人索取那个小信息。

## 仍然需要一起做的几步

1. **T09 真实业务部署**：网络和真实应用/数据层必须接起来才能最终验收。
2. **T11/T12 共享数据与分流验证**：需要真实双实例入口，但代码和测试脚本可以提前写完。
3. **T14 故障实测**：先确认另一台健康、持续请求已开始和恢复步骤明确；之前只能准备脚本，不停实例。
4. **T22 总验收**：可以分批检查，但总验收通过要五项交付与个人签认材料齐全。
5. **T24 正式提交**：最终版本确认后上传，不能拿未完成材料充数。

依赖不能完全消失；这里尽量把等待压缩到短的对接与真实验证窗口。若某人暂时没有共享 Lab 操作权，仍可先做本地代码、配置脚本、测试和文档，并和环境持有人联合执行；没有权限时不共享个人密码，也不声称做过云端测试。

## 防止“等你做完”的日常规则

- 卡片写“需要 A 提供实例入口/角色名”，不写模糊的“等 A 全部完成”。
- 每次工作结束提交当前可用版本，列还没接入的部分；未验收的内容仍保持进行中。
- 接口参数变动写进 interfaces/decisions，并提醒受影响的人；不默默修改端口。
- 架构、测试、成本和报告从第一天滚动维护，最终仅补实际结果和核对。
