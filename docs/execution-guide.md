## 1. 我们最终做出什么

保留一个小而能用的读书记录网页：添加记录、查看记录、显示统计。把背后的系统升级成：

`用户浏览器 → 总入口（负载均衡器） → 两个不同可用区的应用服务器 → 同一份托管数据库`

再加上观察运行情况的监控页面和能真正触发的告警。可用区可以理解为同一地区中分开的机房区域；无状态表示重要数据不能只放在某台应用服务器的内存或本地文件里。

先把“坏一台仍可用、两台读写同一份数据、有告警证据”做好。新账号系统、推荐算法、复杂界面等先不加入范围。是否有真实用户、真实流量必须如实说；可把测试并发量作为设计假设，不能编造用户规模。

**选型草案：**延续 Flask + 两台 EC2 + Application Load Balancer；数据库先比较 DynamoDB 和 Multi-AZ RDS。若只是小型独立书籍记录，可先验证 DynamoDB 路线；若课程实验、查询需求或权限更适合关系数据库，则选 Multi-AZ RDS。选择不是价格结论，最终以需求、可运行性、权限和计算器估算为依据。

### 必须按顺序的主线

1. 定服务与数据库方向 → 写清数据字段和启动约定。
2. 应用能用数据库 → 两台应用运行同一版本。
3. 网络和两台应用都准备好 → 接总入口并联合测试。
4. 联合系统可用 → 实测分流、停一台、告警。
5. 测试通过并保存证据 → 录真实操作视频、定稿文档。
6. 三人核对、签名 → 提交 → 按确认的验收安排清理资源。

**可以提前做：**报告框架、架构初稿、测试脚本、成本假设、视频脚本、部署文档，从第一天开始。**必须等真实结果才能做完：**实际故障结论、最终成本、最终架构图、真实演示视频。停一台服务器的实验不能写成已经完整实测一个 AZ 故障。

## 4. 每一步具体怎么做

任务编号和负责人详见同目录 `TASK_BOARD.md`。以下操作顺序是团队作业流程，不假设实验室具备所有 AWS 权限。

### 第一步：今晚把共同约定写下来（T01–T03）

三个人各花两分钟介绍自己的旧项目，选最容易复现的一份。用一句话写清“谁用它、完成什么、为什么希望不停机”。确认用哪个 Learner Lab 做最终演示，记剩余额度。由 C 整理并询问 tutor：视频时长、自动扩容是否必做、取证后能否拆除、多成员应怎样获得允许的实验访问。

A 建私有代码仓库并按课程规则邀请其他两人；C 建任务板，添加负责人、开始日期、目标日期和前置任务；B 上传清理后的应用代码与依赖清单。不要把整份学习资料目录上传到仓库。

**交接：**C 把会议结论记在 `collaboration_starter/docs/decisions.md`；三人确认，后续修改也记在这里。

### 第二步：先约定代码怎样对接（T04）

B 写一份短约定，A/C 审阅后开始并行：

- 页面保留哪些功能，测试添加记录应出现什么结果。
- 数据字段，例如 `record_id`、`title`、`status`、`pages_read`、`total_pages`、`rating`、`created_at`；主键用不会因同时提交而轻易重复的 ID。
- 配置放环境变量，例如区域、表名、服务器标签；不能在代码里写访问密钥。
- 提供 `/health` 给负载均衡器判断应用是否启动，返回 200 表示进程可响应；数据层读写另设功能测试。不要把“进程活着”当成“数据库一定可用”。
- 例如统一应用端口为 `8000`，统一启动入口；具体命令在依赖和文件名确定后补入 `docs/deploy.md`。两台机器必须一致，Flask 开发服务器不作为最终部署方式。
- 页面或日志显示简短的 `APP_INSTANCE_LABEL` 和代码版本标识，便于演示请求来自不同实例；不要在界面暴露密钥、完整配置或敏感内部信息。

**为什么现在约定：**A 不必等全部功能完成才搭服务器，C 不必等系统上线才写测试。

### 第三步：A 搭基础环境，B 改应用，C 准备检查（T05–T08，并行）

**A：**进入 Learner Lab 后先确认 us-east-1、余额和允许使用的角色。检查能否用两个 AZ、负载均衡、托管数据库、监控和 HTTPS 所需资源。画出 VPC 中每个 AZ 的公有/私有子网、入口、应用及数据路径。确认私有应用怎样访问数据库、下载依赖以及如何维护，再创建最小可测环境；出口或 endpoint 若收费，要记入成本。私有子网里的程序无法下载依赖时，不能只靠反复重启解决，要检查路径。

HTTPS 从第一阶段就验证域名/证书/实验室权限是否可行，不等录视频时才发现不能配置。若受限，保留错误并问 tutor，不画出并未实现的 HTTPS。RDS 路线还需配置独立数据库安全组、跨 AZ 能力和凭证管理；DynamoDB 路线需确认应用角色及访问路径。

**B：**先在自己的开发环境复现旧应用，再把存取数据的代码单独整理，迁到选定数据库。按“创建测试记录 → 查回记录 → 刷新后仍在 → 重启应用后仍在”验证。用 UUID 等唯一标识避免旧代码按秒时间戳加标题导致同秒同名记录覆盖。数据不要只写在本地 JSON 文件；测试使用虚构书籍记录，不导入私人信息。

若 B 无最终环境操作权限，B 提交代码与数据库创建步骤，由 A 在共享屏幕时执行；B 负责指导、解释及核验结果。开发可使用允许的本地替代方式或自己的 Lab，但最终证据来自同一套集成系统。

**C：**先写测试步骤和证据表，列明负载分发、数据共享、故障、告警、安全核对分别怎么验收。准备报告标题、成本表的项目与流量假设、60 秒视频脚本。不要等待截图齐了才开始想要证明什么。

**11/3 检查门槛：**A 能展示环境草图和权限结果；B 能演示一次真实数据库写入及读取；C 有测试表。如果其中一项失败，先解决它，暂不做增强。

### 第四步：把两个应用接到一个入口（T09–T12）

A 按双 AZ 设计创建两个实例，部署 B 已复核的同一个提交版本；不是分别手工修改两台服务器代码。配置目标组（可理解为负载均衡器的服务器名单）、应用端口和健康检查地址，确认两台健康后再通过统一入口访问。应用入站只允许必要来源，不能为了调试长期开放所有端口。

B 在这个入口添加一条记录，验证另一个实例也能读到；检查会话或临时文件是否让用户换服务器就丢数据。部署结果记下代码提交编号和配置，不只记一个网址。

C 发一组小规模、间隔合理的请求，保留时间、响应状态和实例标签。连接复用可能让连续几次请求来自同一台，不要求每次轮流；要有足够结果证明两台都处理过。数据读回若采用最终一致读取，测试应明确预期和等待方式，不能把一切短暂延迟都归为故障。

**11/6 检查门槛：**三人都能通过同一个地址使用功能；两台健康；两台看到相同持久数据；图上每个主要组件都能对应到资源清单。

### 第五步：监控、故障和安全检查（T13–T16）

C 根据真实资源制作 dashboard，至少显示入口请求量/错误、目标健康情况及适当的应用或数据库指标。选择一个有意义的 alarm，例如健康目标数不足或错误率异常。说明为何选它、阈值与统计窗口是什么、怎样测试；通知方式以实验室允许能力为准。保存从正常到 ALARM 再恢复的时间与证据，不能只保存“创建成功”。

故障测试由三人一起做：C 先开始持续请求并记录结果 → A 在已确认另一台健康后停止一台测试实例 → B 操作读写功能 → C 记录失败数、切换时间和恢复结果 → A 恢复环境。先记录目标组的健康检查配置；实际可能有短暂失败，要解释，而不是要求日志一定零失败。

安全检查由 C 提问、A/B 展示：公开入口是什么？应用端口谁能访问？数据库谁能读写？EC2 是否使用允许的角色而非复制旧会话密钥？传输和存储加密实际在哪里配置？是否有未处理限制？把实际情况写入文档，避免再次出现“图是 HTTPS、运行是 HTTP”。

若自动扩容被选为增强，A 配策略、B 保证新实例可复现启动、C 在受控流量下记录扩容与回落。不能仅因 ASG 最小数量设为 2，就说已经证明自动随需求扩容。若改选三个增强主题，要在实施前确认不重复计算 core，并为每个主题留测试和业务理由。

**11/10 检查门槛：**core 证据齐全，未解决问题有负责人；没有证据的增强不能写成已完成。若进度紧，先停止非必要新功能，但课程强制项不能以“降级”省略。

### 第六步：用实际系统生成文档、成本、视频（T17–T21）

- A 将架构图对照资源清单逐项核对：AZ、子网、入口协议、流向、两实例、启动卷、数据层、监控。图不是想象中的目标状态。
- B 汇总每人的章节。重要选择按“需要什么 → 考虑过什么 → 为什么这样选 → 代价/限制 → 实测证据”写。C/A 按部署文档复现关键步骤，缺步骤由原作者补。
- C 使用 AWS Pricing Calculator，选择 us-east-1、12 个月，计算最终架构重要资源。写明实例规格/运行时长、数据量、请求和流量等假设，包含实际选用的负载均衡、磁盘、数据库、日志、出口等。另附实验前后 Lab 余额记录；两者是不同账。
- 视频联合录真实浏览器操作。建议 0–10 秒讲目标及请求路径；10–25 秒现场添加并读取记录；25–45 秒展示已有真实分流或故障测试的关键片段；45–60 秒讲一项选择及代价。长故障测试可剪辑，但标明经过时间，不假装 1 秒完成。是否要求每人出镜以最新课程说明为准。
- 每人整理实际 AI 使用说明、进度截图和个人贡献，不补造历史记录。

### 第七步：交叉检查并提交（T22–T24）

A 查“图与部署一致”；B 查“报告、代码、步骤可复现”；C 查“视频实际操作、成本、证据”。再轮换：A 查 C 的成本，B 查 A 的图，C 查 B 的说明。检查模板残留和密钥，确认所有文件能打开。

Design document 正文严格少于 4,000 词且少于 8 页；架构图及成本估算保守各做 1 页 PDF；视频按 60 秒以内制作，待 tutor 确认冲突。备齐个人签认贡献声明和真实签名封面。指定一名上传者和一名复核者，核对 Moodle 所需代码、文件和提交回执。按已确认的验收安排清理，不要在最终录屏前拆资源，也不要认为 End Lab 就删除了全部资源。

## 5. 三个人怎样共同管理

### 一套信息放在哪里

建议使用 GitHub 私有仓库保存代码与文档，GitHub Projects 管任务，群聊处理即时沟通。Projects 支持表格、看板、时间轴，并能关联代码变更；三种视图读同一份任务，不手工维护三套进度。

如果三人今晚暂时不熟悉 GitHub Projects，先把 `TASK_BOARD.md` 放到现有团队共享文档中，由一个人开会时更新；其他人用各自账号评论。只有一份被指定为正式进度来源，不要在多个副本各打各的勾。本地文件或聊天里的时间表不会自动同步到同学电脑。

### 任务板如何建

1. A 新建仅组员可访问的私有仓库，按权限邀请 B/C；C 新建私有 Project 并单独确认项目访问权限。
2. 每个 T 编号建一张任务卡，复制 `TASK_BOARD.md` 的标题、负责人、日期、前置任务及验收标准；任务模板在 `collaboration_starter/.github/ISSUE_TEMPLATE/task.md`。
3. 状态统一为：**未开始、进行中、等检查、已完成、被卡住**。被卡住时必须写清“缺什么、等谁、何时再检查”。
4. 加字段：开始日期、目标日期、前置任务（文本）、证据位置、检查人。真正的 Assignee 换成实际 GitHub 用户；代号只是本计划占位。
5. 建三个视图：按状态分组的看板；按开始/目标日期显示的时间轴；按负责人分组的表格。
6. 项目的时间轴用于显示计划，不假设它会自动安排前后依赖。上游推迟时，在卡片中 @ 下游负责人并一起改日期。

**状态怎么变：**本人领取 → 进行中；提交代码/文档及证据 → 等检查；检查人确认可用 → 已完成。只装好服务、没有测试和说明，不能标完成。

### 代码怎样一起改

`main` 是大家最近一次确认能工作的版本。每个人从 main 开自己的工作分支，完成后发 Pull Request（可以理解为“请另一位同学检查这次改动”），通过后合回 main。

首次在自己电脑上克隆仓库。以下地址和分支名都是示例，替换为实际值；不要直接把占位文本当命令执行：

```powershell
git clone <你们私有仓库的地址>
cd <仓库文件夹>
git switch main
git pull --ff-only
git switch -c b/t07-database
```

修改并本地验证后，只加入自己本次修改的文件；下面文件名是示例：

```powershell
git add app/data_store.py docs/deploy.md
git diff --cached
git commit -m "T07 connect reading records to database"
git push -u origin b/t07-database
```

然后在 GitHub 打开 Pull Request，写“改了什么、怎么测、证据在哪、有没有未解决问题”。检查人确认后合并。其他两个人接着从 main 拉取；A 部署这个已经合并的版本，并记录 commit 编号。

没有 Git 经验时也可用 GitHub Desktop 完成克隆、分支、提交和推送，原则不变。发生冲突时，不用强推或直接覆盖解决；两位修改者一起确认保留哪段。尽量分文件：A 管 `infra/`，B 管 `app/`，C 管 `tests/`、`evidence/` 和成本/视频草稿；共同文件先约定谁整合。

### AWS 怎样一起做

**共同开发不等于共同登录一个个人账号。**最终系统在同一套允许使用的环境集成，代码由三人各自开发。

- 若课程提供各自身份访问同一环境的方式，按课程方式授权，每人用自己的身份。
- 若 Learner Lab 不提供这种权限，不自行给同学共享账号密码或会话 token。由环境持有人 A 负责最终环境操作；B/C 提交代码、配置和步骤，约时间共享屏幕一起部署、验证及解释。
- B/C 如需在个人 Lab 测试，资源会在各自独立账号，不能假设它们自动组成同一个数据库或负载均衡系统；最终必须在选定环境重做集成测试。
- 程序访问 AWS 资源优先用实验室允许的 EC2 实例角色等机制，避免重复上次把临时凭证复制到服务器的做法。具体角色名称和允许操作先查当前 Lab，不假设可以创建任意 IAM 用户/角色。
- 约定“谁正在改环境”：A 在任务卡记录开始部署、变更、结束部署；测试窗口内不让另一人同时重配相同资源。
- 改坏时先回到上个可用代码版本；涉及数据库结构变化则事前准备数据备份/兼容方案，不能只回滚代码。Reset 会删除实验配置，不能当普通重启使用。

### 每天只需要更新三句话

各自在任务卡写：今天完成了什么（链接）、现在卡在哪里、下一步及预计时间。不是交给某一个人写三人的日报。

若卡住超过约 30–45 分钟，把原始错误、尝试过的操作、需要谁帮助写出来，找对应同学共同排查；权限错误和核心设计冲突尽早问 tutor。内部节点落后半天以上，就更新下游安排，不默默拖到最后。

## 6. 今晚 45 分钟启动清单

- 0–10 分钟：确认课程、选起始服务、认领 A/B/C，写实际名字和各自空闲时间。
- 10–20 分钟：确定最终 Lab 环境持有人；核对预算、权限、数据库候选和 HTTPS 难点。
- 20–30 分钟：建私有仓库与共享任务板，放入 T01–T24；确认谁能访问。
- 30–40 分钟：A/B/C 各讲自己的第一个交付，确认数据/端口/健康检查等对接约定。
- 40–45 分钟：定第一次集成时间、记录 tutor 问题与询问人。

会后第一个动作：A 查权限和网络方案，B 复现旧应用，C 写测试清单。三件事可以同时开始。

## 7. 常见词，用人话解释

| 名称 | 在你们项目里意味着什么 |
| --- | --- |
| GitHub 仓库 | 三个人放同一套代码、保留修改历史的地方 |
| 分支 / Pull Request | 各自先改副本，再请另一人检查后合并 |
| commit | 一次有编号的代码存档；两台服务器要用同一份存档 |
| VPC / 子网 | 你们在 AWS 里的网络范围，以及里面划分的区域 |
| 安全组 | 哪些来源可以访问哪些端口的规则 |
| 可用区 AZ | 同一地区里分开的机房区域，用来降低一起停机的风险 |
| 负载均衡器 / 目标组 | 用户统一访问的入口 / 入口后面可接收请求的服务器名单 |
| 无状态 | 重要记录放共享数据层，不能只存在某一台应用服务器里 |
| IAM 角色 | 程序被允许做哪些 AWS 操作的身份，不是共享个人密码 |
| Dashboard / Alarm | 看运行状态的页面 / 指标异常时进入告警状态的规则 |
